# 跨平台移植指南

Tile2D 的引擎层（`LayoutEngine`、`TileManager`、`DimenManager`）是纯算法：没有一行安卓代码，也没有用任何 JDK 特性。这份文档教你在任意语言/平台上实现一份同款引擎，再接入目标平台的渲染生态。

## 移植前：用什么语言实现

动手之前先回答一个问题：**这份引擎在你的目标平台上用什么语言写？**最常见的错误答案是「用 C/C++ 写一份，然后所有平台 FFI 调用」。这个答案要拆成两种情况，结论完全不同。

### 目标平台的原生语言就是 C/C++

PC 桌面（Win32、Qt 等）、嵌入式、游戏引擎等平台，C/C++ 就是原生语言，直接用 C/C++ 实现引擎是**完全正确的**——「目标语言」就是 C/C++，这份文档照常适用。

### 目标平台不是 C/C++

目标是 Java/Kotlin、C#、Go、Rust、JavaScript 等生态时，**不建议**写一份 C/C++ 核心到处 FFI 调用。注意，这不是「C/C++ 不行」，而是「一份 C/C++ 给所有语言用」这个方案本身有问题：

- **高频小调用的边界开销**。`sync` 在惯性滚动期间每帧可能被调用数十次；每次 `sync` 内部还要回调 `getColWidth/getRowHeight`（每个可见瓦片一次）和 `in/out`（每个进出瓦片一次）。FFI 每次调用都有参数打包、线程状态切换、异常桥接的开销，这些高频小调用累积起来会吃掉算法本身的性能优势。
- **回调是双向的**。引擎要回调宿主语言拿边界、拿尺寸、通知瓦片进出。C 调回宿主语言（JNI 回调、PInvoke 委托、FFI 闭包）比正向调用更贵、更容易出错。
- **类型与内存模型割裂**。C/C++ 侧的对象生命周期、分配器、GC 与宿主语言完全不同。瓦片对象在两边传递时，谁负责释放、如何避免拷贝，会变成长期的心智负担。
- **构建与分发复杂**。一份 C 源码要维护多平台编译配置、ABI 兼容、产物分发；改一行算法要重新构建所有平台的胶水层。
- **调试困难**。跨语言栈上的崩溃和内存问题，比单一语言难定位一个数量级。

| |一份 C/C++ + FFI |目标语言实现 |
|---|---|---|
| 调用开销 | 每次 sync/回调过边界 | 无边界 |
| 回调 | 反向调用昂贵且易错 | 原生调用 |
| 内存模型 | 两套，需手动对齐 | 一套 |
| 构建分发 | 每平台一份编译配置 | 随目标语言打包 |
| 调试 | 跨语言栈 | 单一语言栈 |
| 工作量 | 引擎 + N 个胶水层 | 引擎翻译一次 |

引擎本身是纯逻辑：输入几个数字，输出几个数字，没有任何平台特性。在目标语言里用目标语言实现一份，成本远低于维护一条 FFI 通道。

> 结论：**算法只有一份，实现可以有多个**。C/C++ 原生平台用 C/C++；其他平台用各自的语言各写一份。三个核心模块合计约 1300 行（含注释与调试代码），翻译成本很低，不值得用 FFI 换。

## 可移植性来源

先看源码，三个核心类能跨平台的原因一目了然：

- `import` 里没有任何 `android.*`，连 `java.util.*` 都没有，只依赖自己包内的接口
- 只用基本类型（`int`/`long`/`float`/`boolean`）、数组和循环，没有集合 API、没有 lambda
- `LayoutEngine` 唯一的对象创建是初始化两个 `LayoutModel` 状态对象
- 调试代码（`timeProvider`、`syncTime`）在注释里明确标注了「跨平台可删除」

依赖面：

| 模块 | 依赖 |
|---|---|
| `LayoutEngine` | `BoundaryInterface`、`WindowInterface`、`LayoutModel` |
| `TileManager` | `LongMap<T>`、`TileRecycledPool<T>`、`LongQueue`、`Callback<T>` |
| `DimenManager` | `IntIntMap`、`TileDimenProvider`、`Callback` |

自定义数据结构（`LongMap`/`IntIntMap` 等）的原因和实现见「数据结构」章节，先在目标语言里实现它们，再翻译三个核心模块。

## 第一步：布局引擎（LayoutEngine）

引擎是最独立、最好翻译的模块：只依赖两个接口和一个纯数据对象，算法主体是循环和加减法。建议先移植它，单测通过后再做其他模块。

### 状态与接口

引擎只维护：两个 `LayoutModel`（`original` 记录真实状态、`output` 是输出快照）、视窗宽高、两个滚动开关。对外依赖两个接口：

```text
BoundaryInterface（边界，闭区间，支持 MIN/MAX）：
    getLeftBound() / getTopBound() / getRightBound() / getBottomBound()

WindowInterface（视窗交互）：
    in(column, row)                  瓦片进入视窗
    out(column, row)                 瓦片离开视窗
    onWindowCalculated(cs, rs, ce, re) 新视窗计算完毕
    getColWidth(column)              列宽
    getRowHeight(row)                行高
```

目标语言用接口/协议/trait 表达即可，实现方分别是瓦片管理器和尺寸管理器。

### sync：滚动核心

`sync(dx, dy)` 按像素位移滚动。dx/dy 是**视觉位移**：正数 dx 使内容向右移动（视窗向左扩展）。完整流程：

```text
sync(dx, dy):
    # 1. 合法性短路
    if 视窗越界或窗口尺寸 <= 0:
        return false

    # 2. 偏移叠加
    offsetX += dx
    offsetY += dy

    # 3. 水平同步（垂直完全同理，把列换成行）

    # 3a. 内容未填满且已到右边界：尝试右对齐
    if offsetX <= 0 且 totalWidth + offsetX < windowWidth 且 colEnd == rightBound:
        offsetX += windowWidth - (totalWidth + offsetX)

    # 3b. 向右拖，锚点左移，纳入新列
    while offsetX > 0 且 colStart > leftBound:
        colStart--
        offsetX -= getColWidth(colStart)
        totalWidth += getColWidth(colStart)

    # 3c. 向左拖，锚点右移，移出旧列
    while offsetX < -getColWidth(colStart) 且 colStart < rightBound:
        offsetX += getColWidth(colStart)
        totalWidth -= getColWidth(colStart)
        colStart++

    # 3d. 已到左边界：钳位
    if offsetX > 0 且 colStart == leftBound:
        offsetX = 0

    # 3e. 内容填不满，向右扩展右锚点
    while totalWidth + offsetX < windowWidth 且 colEnd < rightBound:
        colEnd++
        totalWidth += getColWidth(colEnd)

    # 3f. 内容超出太多，收缩右锚点
    while totalWidth + offsetX - getColWidth(colEnd) > windowWidth 且 colEnd > colStart:
        totalWidth -= getColWidth(colEnd)
        colEnd--

    # 4. 垂直同步（同上）

    # 5. 通知视窗计算完毕（瓦片管理器据此做濒死区清理）
    onWindowCalculated(colStart, rowStart, colEnd, rowEnd)

    # 6. 范围变化时更新 original 并 diff
    if 范围变化:
        更新 original
        diff(旧范围, 新范围)
```

> 关键约束：`offsetX` 始终保持在 `[-当前列宽, 0]`，`offsetY` 保持在 `[-当前行高, 0]`。这是「像素精度不退化」的基础，翻译时不要改动任何边界条件。

### seek：定义原点

`seek(column, row, offsetX, offsetY)` 跳转到指定坐标：

```text
seek(column, row, offsetX, offsetY):
    if 边界为空或目标越界:
        return false

    从 (column, row) 向右下扩展：
        逐行累加行高，直到填满窗口高度或到底部边界（过程中调用 in() 预加载）
        逐列累加列宽，直到填满窗口宽度或到右边界

    写入 original（锚点 = column,row，offset 置 0）
    调用 sync(offsetX, offsetY) 完成微调
```

### diff：区域差异

计算新旧视窗矩形的差异，确定哪些瓦片 out、哪些 in：

```text
if 新范围与旧范围完全不相交:
    旧范围全部 out()
    新范围全部 in()
else:
    求并集，按「上、右、下、左」四个区域分解
    每个格点：只在旧范围 → out()；只在新范围 → in()
```

Java 实现把并集拆成四块区域逐格判断，避免对整个大矩形双重遍历；其他语言直接照搬即可。

### 尺寸变更补偿

`updateWidth/updateHeight/updateSize` 在瓦片尺寸变化时调整偏移，保持视觉稳定。补偿方向由 gravity 决定：

| gravity | 列宽变化 | 偏移补偿 |
|---|---|---|
| `START`(-1) | 右侧扩展/收缩 | `offsetX` 不变 |
| `CENTER`(0) | 两侧均匀 | `offsetX += (oldWidth - newWidth) / 2` |
| `END`(1) | 左侧扩展/收缩 | `offsetX += oldWidth - newWidth` |

只对「当前在视窗内」的列/行做扰动；范围外的直接更新 `totalWidth/totalHeight` 即可。

### 边界检测与辅助方法

- `isAtLeftBound/isAtTopBound`：`锚点 == 边界 && offset == 0`
- `isAtRightBound/isAtBottomBound`：`colEnd == 边界 && totalWidth + offsetX == windowWidth`
- `min/max`：Java 实现用 int/float 重载（避免装箱）；其他语言用原生 `min/max` 或直接比较

### 调试代码

`timeProvider` 和 `syncTime` 只用于统计 `sync` 耗时，移植时整段删除，不影响任何行为。

## 第二步：数据结构

瓦片管理器依赖三个自定义数据结构。先在目标语言里实现（或用现成库），原因和方案如下。

### 长整型映射（LongMap）

活跃/濒死瓦片用 `long` 作 key 存 `T`。需求：

- `get/put/remove/size/containsKey/clear`
- 迭代器：`next/key/value/remove`，支持删除模式（边遍历边删）

各语言方案：

| 语言 | 方案 |
|---|---|
| Java | 包内实现：`LongMapOpenHashMap`（开地址哈希，无装箱，默认）、`LongMapSparseArray`、`LongMapHashMap`；或 `fastutil`、`trove` |
| Kotlin/JVM | 同上 |
| C# | `Dictionary<long, T>`（long 是值类型，无装箱） |
| Go | `map[int64]T` |
| Rust | `std::collections::HashMap<i64, T>` |
| C++ | `std::unordered_map<int64_t, T>` |
| JS/TS | `Map<number, T>` |
| Swift | `Dictionary<Int64, T>` |

> 为什么 Java 不用 `HashMap<Long,T>`：key 装箱成 `Long` 对象，瓦片进出视窗频繁，装箱/拆箱和哈希开销会被放大。接口很小，自定义实现只有几百行。其他语言没有装箱问题，直接用标准库即可。

### 整型键值映射（IntIntMap）

列宽/行高用 `int -> int`，比 LongMap 多一个 `get(key, defaultValue)`。方案同上：Java 可用 `fastutil` 的 `Int2IntOpenHashMap` 或 `SparseIntArray`；C# `Dictionary<int, int>`、Go `map[int]int`、Rust `HashMap<i32, i32>`、C++ `std::unordered_map<int, int>`。

### 整型映射（IntMap）

回收池按类型分组需要 `int -> 队列` 的映射，接口与 LongMap 同构（key 换成 int），value 用目标语言的队列类型。

### 瓦片回收池（TileRecycledPool）

按类型分组的瓦片缓存：`get(type)` 取队头（空返回 null）、`recycle(type, tile)` 放回、`reset()` 清空、`moveTo()` 整体迁移。队列用各语言自带：Java `ArrayDeque`、C# `Queue<T>`、Go 切片、Rust `VecDeque<T>`、JS 数组。

### 瓦片 ID 编码

活跃/濒死瓦片用 `long` 做 key：高 32 位列号、低 32 位行号：

```text
id = (column << 32) | (row & 0xFFFFFFFF)
column = id >> 32
row = id & 0xFFFFFFFF
```

- 有 64 位整数的语言直接照搬
- JavaScript 的位运算只有 32 位，两个替代：`"col,row"` 字符串作 key（最简单），或 `(col << 16) | row` 的 32 位编码（col/row 各 16 位范围），或 `BigInt`
- 其他语言也可以用字符串 key，代价是慢一点

### 瓦片持有者（BaseTileHolder）

字段 `column/row/width/height/type` + 可选生命周期钩子 `onRecycled/onInWindow/onOutWindow/onSizeChanged`。目标语言用基类/接口/trait 表达。

## 第三步：瓦片管理器（TileManager）

### 四状态池

| 池 | 存储 | 含义 |
|---|---|---|
| 活跃 | `LongMap<T>` | 当前在视窗内可见 |
| 濒死 | `LongMap<T>` | 刚离开视窗（视窗外扩展一圈的缓冲） |
| 预取 | `LongMap<T>` | 朝运动方向提前加载（已创建绑定，尚未进窗） |
| 回收 | `TileRecycledPool<T>` | 已回收可复用 |

流转：

```text
进入视窗 → 活跃池（预取池瓦片直接转正，跳过创建绑定）
离开视窗 → 濒死池（未启用濒死区则直接回收）
离开濒死区 → 回收池
方向反转 → 预取池淘汰（直接回收，不进濒死区）
复用 → 活跃池
```

### in / out / obtain / recycle

```text
in(column, row):
    先从濒死池查 id
    命中 → 移入活跃池（跳过绑定）
    未命中 → obtain(type) 创建或复用 → 绑定 → 入活跃池
    回调 onInWindow + onTileIn

out(column, row):
    移出活跃池
    回调 onOutWindow + onTileOut
    启用濒死区 → 入濒死池；否则直接回收

obtain(type):
    回收池取 → 有则复用；无则 onCreateTileHolder(type)

recycle(tile):
    入回收池 + 回调 onRecycled + onTileRecycled
```

### 濒死区

濒死区 = 视窗向外扩展 `dyingExpand` 圈（默认 1）。**边界计算不要用减法**：`colStart - leftBound` 在边界是 `Integer.MIN_VALUE` 时会溢出（数学距离超过 int32，减法结果不可信）。正确做法是逐格行走，每步判断是否已到边界：

```text
getDyingLeft():
    left = colStart
    for i in 0 until dyingExpand:
        if left <= leftBound: break
        left--
    return left
```

`diffDying(colStart, rowStart, colEnd, rowEnd)` 在每次视窗计算后调用，把超出濒死区的瓦片清到回收池。`setDyingEnabled(false)` 关闭濒死区时，离开视窗的瓦片立即回收，并清空濒死池。

### 预取区

预取与濒死对称：**濒死向后留，预取向前抢**。预取瓦片已创建绑定但不进活跃区（`in()` 时直接从预取池摘出转正，不触发进窗回调）。**默认开启**。

- **方向预测**：`diffPrefetch` 记录上次视窗锚点，与本次锚点做三值比较得出八方向位移。首帧/跳转后闭区间为空（`start > end`）表示无上次记录，方向未知，不扩展。
- **非对称矩形**：预取区只朝运动方向扩展 `prefetchExpand` 圈（默认 1），其余三边贴合视窗本体。视窗未动（`sameWindow`）时保留已预取瓦片，不重排。
- **条带入队**：每帧清空队列重排，只把「方向矩形 − 视窗矩形」的前方条带坐标入队（`enqueueRegion`，三池均未持有才入队）。不做数量上限，条带宽度自然约束。
- **帧预算消费**：渲染端每帧调用 `drainPrefetch()`，内部按 `prefetchPerFrame` 个消费（默认 8，可通过 `setPrefetchPerFrame` 调整；二维网格吞吐，RV 一维是 4），队列有剩余就续挂下一帧回调，空了自然停止。
- **淘汰**：方向反转时，落在新方向矩形之外的预取瓦片直接回收，不进濒死区——它从未进过窗，没有可见生命周期，不需要缓冲。
- **峰值观测**：`prefetchQueuePeak` 记录队列高水位，随预取区生命周期归零（关闭预取/clearAll/跳转时清零），调试面板展示「预取峰值」。

队列用 `LongQueue`（long 先进先出，环形数组、2 的幂容量、自动扩容）。

### 更新操作

`update/updateRange/updateColumn/updateRow` 刷新指定范围的瓦片：活跃区内的先回收再重新 `in`（重新绑定）；濒死区内的只刷新已缓存的数据。`updateAll` 等价于原地 `seek`。

### 存储替换

活跃/濒死/回收三个池都支持整体替换（换数据结构实现），迁移流程：清空目标容器 → 逐个搬入 → 清空旧容器。

## 第四步：尺寸管理器（DimenManager）

### 三级优先级

```text
1. 单独设置的尺寸（IntIntMap）
2. TileDimenProvider 提供的动态值
3. setDefault 默认尺寸
```

`getTileWidth(column)` 按此顺序查询。`TileDimenProvider` 是自定义接口（`getTileWidth/getTileHeight/set*/delete*`），各平台按需实现，例如根据内容测量动态返回。

### 修改流程

`setTileWidth(column, width, gravity)`：

```text
1. width <= 0 → 拒绝（设置方法要求必须大于 0）
2. 边界为空或 column 越界 → 拒绝
3. 与旧值相同 → 直接返回
4. 遍历濒死区内该列的所有瓦片，调用 resizeTile 同步尺寸
5. 调用引擎 updateWidth 做视窗补偿
6. 触发 UI 刷新
```

删除自定义尺寸请用 `deleteTileWidth(column, gravity)`（`widths.remove` + 同样的同步流程），**不再用传 0 表达删除**。`setTileHeight` 同理；`setTileSize` 把横竖两个方向合并为一次扰动（宽高都必须大于 0）。

## 第五步：组合调度层（TileCoreService）

调度层把三个模块组合成统一入口，本身也是纯逻辑，可以移植。其中 **EventHandler 是安卓相关的（GestureDetector、Scroller），不要移植**——各平台用自己的输入体系（触摸、鼠标滚轮、手柄等）把位移转成 `sync(dx, dy)` 调用即可，惯性滚动也由目标平台自己的动画机制驱动。

调度层的职责：

- 转发边界/尺寸/瓦片生命周期回调（把引擎和瓦片管理器接起来）
- 提供统一 API：`sync/seek/snap/update/setTileWidth/...`
- 在 `onWindowCalculated` 后调用 `diffPrefetch` 规划预取，由渲染端每帧 `drainPrefetch()` 消费（帧回调按「调试开启或队列非空」驱动，两者皆无自然停止）
- 持有调试统计（可选）

## 第六步：接入目标平台渲染层

引擎只输出「哪些瓦片可见、在哪个坐标、多大」，渲染层负责画出来。接入方式参照安卓平台扩展指南：

1. 实现 `BoundaryInterface`/`WindowInterface`/`Callback`（数据源与瓦片持有者）
2. 把「视窗变化」通知接到目标平台的刷新机制（重绘/重组/提交渲染命令）
3. 用目标平台的输入体系驱动 `sync`

## 测试策略

三个模块都是纯算法，非常适合作单元测试：mock 接口，验证输出。

- **LayoutEngine**：mock 边界与视窗接口，验证滚动/跳转/尺寸变更场景下 `LayoutModel` 输出
- **TileManager**：mock 回调，验证瓦片进出与回收计数；预取场景下验证方向预测、条带入队、队列消费与方向反转淘汰
- **DimenManager**：mock 回调，验证尺寸查询与修改扰动

边界场景清单：

- 空边界（left > right）
- 单列/单行
- 从 `Integer.MIN_VALUE` 附近起步
- 高频抖动（在同一列边界反复滚动）
- 尺寸反复修改（从大到小再到大）
- 全部瓦片返回 null（稀疏场景）
- 内容比视窗小（填不满）
- 极端跳转（一次跨过整个 int32 空间）
- 预取首帧（无上次记录，方向未知，不扩展）
- 预取方向反转（身后预取瓦片被淘汰回收）
- 预取队列峰值（快速反复甩动，验证不失控膨胀）
