# 跨平台移植指南

Tile2D 的引擎层（`LayoutEngine`、`TileManager`、`DimenManager`）是**纯算法**：没有一行安卓代码，也不依赖任何集合库。本文先把最容易翻错的 `sync` 逐块讲透，再讲怎么自己实现数据容器、以及其余模块。

## 一、先定语言：别做「一份 C/C++ 核心 + 到处 FFI」

- **目标平台的原生语言是什么，就用什么语言实现一份引擎。**
- 不建议「用 C/C++ 写一份，所有平台 FFI 调用」——不是 C/C++ 不行，而是这个方案本身有问题：
  - **高频小调用**：惯性滚动时 `sync` 每帧可能被调几十次，内部还会回调 `getColWidth`/`in`/`out`（每个可见/进出瓦片一次）。跨语言边界的参数打包、线程状态切换累积起来会吃掉算法本身的优势。
  - **回调是双向的**：引擎要反向调宿主拿尺寸、通知进出，反向调用比正向更贵更易错。
  - **两套内存模型**：对象生命周期/GC 要手动对齐，长期心智负担。
  - 构建分发要维护 N 份编译配置；跨语言栈的崩溃很难查。

| | 一份 C/C++ + FFI | 目标语言各写一份 |
|---|---|---|
| 调用开销 | 每次 sync/回调都过边界 | 无边界 |
| 回调 | 反向调用，昂贵易错 | 原生调用 |
| 内存模型 | 两套 | 一套 |
| 构建分发 | 每平台一份 | 随语言打包 |

> **算法只有一份，实现可以有多个**，翻译成本远低于维护一条 FFI 通道。

## 二、为什么它能跨平台

看源码就明白了：不 `import` 任何平台包（连 `java.util.*` 都没有）；只用 `int/long/float/boolean` + 数组 + 循环，没有集合 API、没有 lambda；`LayoutEngine` 唯一的对象创建是初始化两个 `LayoutModel`；调试代码（`timeProvider`/`syncTime`）已标注「可删除」。

对外只依赖两个接口：

```text
边界接口（闭区间，支持 MIN/MAX）：
    getLeftBound() / getTopBound() / getRightBound() / getBottomBound()
视窗接口：
    in(列, 行) / out(列, 行)        瓦片进入 / 离开视窗
    onWindowCalculated(首列, 首行, 末列, 末行)   新视窗算完了
    getColWidth(列) / getRowHeight(行)          列宽 / 行高
```

## 三、`sync` 的完整逻辑（全中文伪代码）

约定：`dx/dy` 是**视觉位移**——正的 `dx` 表示**内容向右移动**（也就是视窗在往左看）。伪代码用中文名字，末尾附「中文名 ↔ 代码字段」对照。

```text
同步(横向位移, 纵向位移):

    ── ⓪ 合法性短路 ──
    如果 视窗范围为空（首列>末列 或 首行>末行） 或 窗口宽<=0 或 窗口高<=0:
        返回「没算」

    ── ① 横向同步（纵向完全同构）──
    如果 横向滚动开启:

        左偏移 = 上次左偏移 + 横向位移        ← 偏移的叠加，只在本分支内

        // Ⓐ 内容比窗口窄、且已经贴到数据右边界 → 直接右对齐
        如果 内容宽 + 左偏移 < 窗口宽 且 末列 == 数据右边界:
            左偏移 = 窗口宽 - 内容宽

        // Ⓑ 内容往右移（左偏移 > 0）→ 起点锚点左移，纳入左边的列
        循环 左偏移 > 0 且 首列 > 数据左边界:
            首列 -= 1
            列宽 = 取列宽(首列)
            左偏移 -= 列宽
            内容宽 += 列宽

        // Ⓒ 内容往左移（左偏移 < -当前首列宽）→ 起点锚点右移，丢弃左边的列
        当前列宽 = 取列宽(首列)
        循环 左偏移 < -当前列宽 且 首列 < 数据右边界:
            左偏移 += 当前列宽
            内容宽 -= 当前列宽
            首列 += 1
            当前列宽 = 取列宽(首列)

        // Ⓓ 起点锚点一步跨过了末列锚点 → 让末列跟着跳过来
        如果 首列 > 末列:
            末列 = 首列
            内容宽 = 当前列宽

        // Ⓔ 已经贴到数据左边界 → 钳位
        如果 左偏移 > 0 且 首列 == 数据左边界:
            左偏移 = 0

        // Ⓕ 内容填不满窗口 → 向右扩，补上右边的列
        循环 内容宽 + 左偏移 < 窗口宽 且 末列 < 数据右边界:
            末列 += 1
            内容宽 += 取列宽(末列)

        // Ⓖ 内容超出窗口太多 → 向右缩，扔掉用不到的末列
        末列宽 = 取列宽(末列)
        循环 内容宽 + 左偏移 - 末列宽 > 窗口宽 且 末列 > 首列:
            内容宽 -= 末列宽
            末列 -= 1
            末列宽 = 取列宽(末列)

        // Ⓗ 上面两个循环可能又在右边挖出一个缝 → 再补一次
        如果 内容宽 > 窗口宽 且 内容宽 + 左偏移 < 窗口宽 且 末列 == 数据右边界:
            左偏移 = 窗口宽 - 内容宽

        写回 左偏移

    ── ② 纵向同步 ──
    把上面整段里的「列→行、首列→首行、末列→末行、左偏移→上偏移、内容宽→内容高、窗口宽→窗口高、数据左/右边界→数据上/下边界」全部替换，逻辑一字不改。两个方向的偏移各自在自己的分支里叠加，互不干涉。

    ── ③ 收尾 ──
    通知宿主：视窗算完了(首列, 首行, 末列, 末行)
    如果 视窗范围（四个锚点）发生了变化:
        更新「上次状态」
        做差异：算清楚哪些瓦片进来、哪些出去（谁 in、谁 out）
    返回「算过了」
```

**中文名 ↔ 代码字段对照**

| 伪代码 | 代码 | 伪代码 | 代码 |
|---|---|---|---|
| 首列 / 末列 | `colStart` / `colEnd` | 内容宽 | `contentWidth` |
| 首行 / 末行 | `rowStart` / `rowEnd` | 内容高 | `contentHeight` |
| 左偏移 / 上偏移 | `offsetX` / `offsetY` | 窗口宽 / 高 | `windowWidth` / `windowHeight` |
| 上次左偏移 | `original.offsetX` | 取列宽 / 行高 | `getColWidth` / `getRowHeight` |
| 数据左/上/右/下边界 | `leftBound`/`topBound`/`rightBound`/`bottomBound` | 做差异 | `diff` |

## 四、逐块解读：能做什么、为什么这样、去掉会怎样

### ⓪ 合法性短路

- **能做什么**：视窗还没初始化（区间为空）或窗口尺寸为 0 时直接返回，不干活。
- **为什么**：这些状态下算出来的锚点范围毫无意义，传出去会让宿主去创建一堆莫名其妙的瓦片。
- **去掉会怎样**：容器尺寸还没测量（首帧）、或边界为空时，会算出非法范围并向外传播。

### ① 偏移的叠加（放在分支内，且在所有判定之前）

- **能做什么**：把本方向的位移并进偏移。
- **为什么**：下面每个判定/循环读的都是它，必须先是最新的；同时它**只在本方向生效**。
- **去掉（或挪到方法开头统一叠加）会怎样**：判定会读到「已经加过位移」的值——比如 Ⓐ 的 `内容宽+左偏移 < 窗口宽` 和「`左偏移` 里已经有位移」叠在一起，条件会退化成恒真/恒假（换符号也救不回来）；另外，当该方向滚动被关闭时，位移仍会被写进偏移，直接破坏后面的不变式。

### Ⓐ 右对齐（试探性补偿）

- **能做什么**：把内容整体**右对齐**（等价于「伪造一次向右拖」），从而给 Ⓑ 一个机会，把左边的列拉进来把窗口补满。
- **为什么叫「试探性」**：它推出来的偏移有下游兜底——Ⓑ 会用「纳入新列」把它消费掉；如果左边已经没有列可纳入（首列已到数据左边界），Ⓔ 会把它**强制归零**。
- **去掉会怎样**：靠近数据右端、且内容不满一屏时，左边的列不会被补进来，窗口一侧会露出空白。

### Ⓑ 向右移：纳入左边的列

- **能做什么**：只要左偏移超过一整列的宽度，就把左边一列纳进来（首列 −1），并把这个列宽从偏移里扣掉、加到内容宽上。
- **为什么逐列、而不是一次算总位移**：列宽**可变**，偏移必须始终保持在「不到一列宽」的范围内，只能按实际列宽一格一格地消费。
- **去掉会怎样**：往右拖时左边不会出现新列 → 左边露白、内容断档。

### Ⓒ 向左移：丢弃滚过去的列

- **能做什么**：偏移已经超过当前首列宽时，把首列右移一格，把它的宽度从偏移里加回、从内容宽里扣掉。
- **为什么必须做**：滚出窗口的列留着没有意义。
- **去掉会怎样**：范围会无限增长——内存、绘制量、遍历次数都跟着涨；而且 `内容宽` 虚高，后续判定全偏。

### Ⓓ 末列跟随（3c-2）

- **能做什么**：当一次位移让**首列一步跨过了末列**（区间变空）时，把末列拉过来对齐首列，内容宽重置为「一列」。
- **为什么必须做**：Ⓒ 只移动首列，末列还停在旧位置且内容宽已被扣得很小；此时如果直接进入 Ⓕ 的填充循环，它会把**刚刚跨过、已经扣掉的那些列**当成「新列」重新问一遍宽度（大位移时接近双倍遍历）。
- **去掉会怎样**：大位移（甩动、跳转）时遍历次数几乎翻倍，中间态还会出现「内容宽 与 锚点区间」不一致。

### Ⓔ 左边界钳位

- **能做什么**：偏移为正（内容右移、左边要露白）且首列已到数据左边界时，把偏移归零。
- **为什么**：左边已经没有内容了，Ⓑ 也没列可纳入，只能左对齐收场。
- **去掉会怎样**：左边会露白，并且偏移跑出不变式范围（下一帧判定会连锁出错）。

### Ⓕ 向右扩：补满窗口

- **能做什么**：内容宽 + 偏移仍然小于窗口宽（填不满）时，不断把末列往右加，直到填满或触及数据右边界。
- **为什么必须做**：宿主只渲染「首列..末列」这个区间，不扩的话右边就是空的。
- **去掉会怎样**：窗口右侧露白；跳转/缩放到边界附近时尤其明显。

### Ⓖ 向右缩：扔掉多余的末列

- **能做什么**：如果**去掉末列之后仍然填得满**（说明末列是多余的），就把它扔掉，继续检查新的末列。
- **为什么判据是「去掉末列后仍填得满」**：这样能保证末列是「最后一个还需要的列」，让内容最多只超出一列以内。多出来的列纯属白算、白画。
- **去掉会怎样**：窗口右边会挂着一整排看不见的列；大位移（跨列多）时，绘制量/遍历量会明显虚高。

### Ⓗ 终态补偿（3g）

- **能做什么**：Ⓖ 收缩之后可能又在右边挖出一个缝，这里再右对齐一次补掉。
- **为什么和 Ⓐ 不对称（这是很多人会想「能不能合并」的地方）**：
  - Ⓐ 是**试探**——它推出来的偏移有下游兜底（Ⓑ 消费、Ⓔ 归零），所以它可以「先推了再说」。
  - Ⓗ 是**终态**——它跑完就写快照出结果，**没有任何下游能撤销它**，所以它必须自己先证明这一推是安全的：`内容宽 > 窗口宽` 保证右移后左边缘不露白，`内容宽 + 偏移 < 窗口宽` 保证右边确实还有缝。
- **去掉会怎样**：右边界附近偶尔会留下一条缝（典型是 Ⓖ 刚缩完那一帧）。

### ⑨ 写回偏移 / 纵向同构 / 收尾

- **写回偏移**：偏移是**相对于首列**的，所以 Ⓑ/Ⓒ 动了首列时，偏移必须同步调整，否则画面会跳。每帧结束要把最终值写回状态。
- **纵向同构**：把列换成行、宽换成高照抄一遍即可。横向与纵向的偏移各自独立叠加——不要图省事抽成一个公共函数，那要么传一堆参数、要么包闭包，反而更难读更慢。
- **onWindowCalculated 要在 diff 之前**：先把「完整的新范围」告诉宿主（宿主据此清理濒死区、规划预取），再做 `diff`（只负责瓦片进出）。顺序反了，宿主会按旧范围规划缓冲。
- **不变式**：每帧结束必须满足 `左偏移 ∈ [-当前首列宽, 0]`、`上偏移 ∈ [-当前首行高, 0]`。偏移是像素级的小数，一旦跑出这个范围，说明「首列」的定义漂了，下一帧的判定会连锁出错。这是「像素精度不退化」的基础。

## 五、其它核心方法

### `seek(列, 行, 偏移X, 偏移Y)`：定义原点（距离无关跳转）

```text
seek(列, 行, 偏移X, 偏移Y):
    如果 边界为空 或 目标越界: 返回「没算」
    从 (列, 行) 向右下预铺一屏（每个格点都调 in() 预加载，避免首帧空洞）
    把锚点写成 (列, 行)、偏移清零，并强制同步到输出快照
    调用 同步(偏移X, 偏移Y) 做微调
```

三个要点：

1. **累加器初值**：预铺时累加 `内容宽` 要从 `trunc(偏移X)` 起算，末尾再减 `trunc(偏移X)`，两者抵消得到纯「宽度和」。**不要**从 0 起算却仍减 `偏移X`——那会整整多减一个偏移，`内容宽` 偏小/偏大，扩展循环的终止列也跟着偏一列。
2. `seek` 把参数当 `dx/dy` 交给 `sync`（偏移先清零），靠分支内那层叠加完成微调。所以**某方向滚动关闭时，该方向的参数不生效**——这是有意为之。
3. **调用方要负责清场**：跳转是「重置视窗」，实现渲染层的容器（`TileManager`/自绘容器）要先把当前所有活跃瓦片清掉再 `seek`；否则旧范围里没被新范围覆盖到的瓦片会**永久残留**（表现为跳转前的画面定格在新画面下面，且 DOM/缓存只增不减）。

### `diff(旧范围, 新范围)`：区域差异

```text
如果 新范围与旧范围完全不相交:
    旧范围全部 out()；新范围全部 in()
否则:
    求并集，拆成「上、右、下、左」四块
    每格判断：只在旧范围 → out()；只在新范围 → in()
```

拆成四块是为了只遍历「并集 − 交集」的那一圈，避免对大矩形双重遍历。

### 尺寸变更补偿 `updateWidth / updateHeight / updateSize`

| gravity | 含义 | 偏移补偿 |
|---|---|---|
| `START`(-1) | 只往右扩展/收缩 | `偏移` 不变 |
| `CENTER`(0) | 两侧均匀 | `偏移 += (旧尺寸 − 新尺寸) / 2` |
| `END`(1) | 只往左扩展/收缩 | `偏移 += 旧尺寸 − 新尺寸` |

只有「当前在视窗内的列/行」需要扰动偏移；范围外的列/行只更新 `内容宽/高` 即可。

### 边界检测

- 左/上：`锚点 == 边界 且 偏移 == 0`（精确）。
- 右/下：`末列 == 边界 且 内容宽 + 偏移 == 窗口宽`（**精确比较**，语义是「像素级对齐」）。

> 右/下这里之所以敢用 `==`：补偿写的是 `偏移 = 窗口宽 − 内容宽`，右边是**两个整数相减**，结果精确可表示，赋给浮点后 `内容宽 + 偏移 == 窗口宽` 按构造成立。若你想要「半个像素内也算到边」，那要显式加容差——那是另一套语义，别混进来。

## 六、自己实现数据容器

瓦片管理器需要几个「以整数为 key」的小容器。**先实现它们，再翻译三个核心模块**。

### 长整型映射（`LongMap`，key 用瓦片 id）

需求：`get/put/remove/size/containsKey/clear`；迭代器支持**边遍历边删**。

| 语言 | 方案 |
|---|---|
| Java / Kotlin | 包内自实现（开地址哈希，无装箱），或 `fastutil`/`trove` |
| C# | `Dictionary<long, T>`（long 是值类型，不装箱） |
| Go | `map[int64]T` |
| Rust | `HashMap<i64, T>` |
| C++ | `unordered_map<int64_t, T>` |
| JS/TS | `Map<number, T>` |
| Swift | `Dictionary<Int64, T>` |

> Java 为什么不直接用 `HashMap<Long,T>`：key 会被装箱成 `Long` 对象，而瓦片进出视窗非常频繁，装箱/拆箱和哈希开销会被放大。接口很小，自己实现只要几百行。其他语言没有装箱问题，标准库直接用。

### 整型映射（`IntIntMap` / `IntMap`）

- `IntIntMap`：列宽/行高用 `int -> int`，比 `LongMap` 多一个 `get(key, 默认值)`。
- `IntMap`：回收池按类型分组用 `int -> 队列`，与 `LongMap` 同构，value 换成队列。

### 瓦片回收池

按类型分组缓存瓦片：`get(type)` 取一个（空则返回 null）、`recycle(type, tile)` 放回、`reset()` 清空、`moveTo()` 整体迁移。队列用语言自带即可（Java `ArrayDeque`、C# `Queue<T>`、Go 切片、Rust `VecDeque`、JS 数组）。

### 瓦片 id 编码

```text
id = (列 << 32) | (行 & 0xFFFFFFFF)      // 高 32 位列号，低 32 位行号
列 = id >> 32
行 = id & 0xFFFFFFFF
```

- 有 64 位整数的语言直接照搬。
- **JavaScript 的位运算只有 32 位**，两个替代：用 `"列,行"` 字符串当 key（最简单），或用 `(列 << 16) | 行` 的 32 位编码（列/行各限 16 位），或 `BigInt`。
- 其他语言也可以用字符串 key，代价是慢一点。

### 瓦片持有者

字段：`列/行/宽/高/类型`；可选生命周期钩子：`onRecycled`（被回收）、`onInWindow`/`onOutWindow`（进入/离开视窗）、`onSizeChanged`（尺寸变化）。目标语言用基类/接口/trait 表达。

## 七、瓦片管理器（`TileManager`）

### 四状态池

| 池 | 存储 | 含义 |
|---|---|---|
| 活跃 | `LongMap` | 当前在视窗内可见 |
| 濒死 | `LongMap` | 刚离开视窗（视窗外扩展一圈的缓冲，短暂保留） |
| 预取 | `LongMap` | 朝运动方向提前加载（已创建绑定，尚未进窗） |
| 回收 | 回收池 | 已回收，可复用 |

```text
进入视窗 → 活跃池（若来自预取池，直接转正、跳过创建绑定）
离开视窗 → 濒死池（未启用濒死区则直接回收）
离开濒死区 → 回收池
方向反转 → 预取池淘汰（直接回收，不进濒死区）
```

```text
in(列, 行):
    先查濒死池：命中 → 移入活跃池（跳过绑定）
    未命中 → obtain(类型) 创建或复用 → 绑定 → 入活跃池
    回调 onInWindow + onTileIn
out(列, 行):
    移出活跃池 → 回调 onOutWindow + onTileOut
    启用濒死区 → 入濒死池；否则直接回收
obtain(类型):   回收池有则复用；无则 onCreateTileHolder(类型)
recycle(瓦片):  入回收池 + 回调 onRecycled + onTileRecycled
```

### 濒死区

濒死区 = 视窗向外扩 `dyingExpand` 圈（默认 1）。**边界不要用减法算**：

```text
错误：left = 首列 - 濒死圈数          // 边界是 Integer.MIN_VALUE 时减法会溢出
正确：逐格走
getDyingLeft():
    left = 首列
    重复 濒死圈数 次:
        如果 left <= 数据左边界: 跳出
        left -= 1
    return left
```

数学距离超过 int32，减法结果不可信；逐格行走每步判断是否到边界即可。每次视窗算完后调用 `diffDying(范围)`，把超出濒死区的瓦片清进回收池。

### 预取区

预取与濒死对称，方向相反：**濒死向后留，预取向前抢**。预取瓦片已创建绑定但不进活跃区（`in()` 时直接从预取池摘出转正，不触发进窗回调）。默认开启。

- **方向预测**：记录上次视窗锚点，与本次锚点做三值比较得出方向。首帧/跳转后没有上次记录 → 方向未知，不扩展。
- **非对称矩形**：只朝运动方向扩 `prefetchExpand` 圈，其余三边贴住视窗本体。视窗没动时保留已预取瓦片、不重排。
- **条带入队**：每帧清空队列重排，只把「方向矩形 − 视窗矩形」的前方条带入队（三池都没持有才入队）。不做数量上限，条带宽度自然约束。
- **帧预算消费**：渲染端每帧调用 `drainPrefetch()`，按 `prefetchPerFrame` 个消费（默认 8）。有剩余就续挂下一帧，空了自然停止。
- **淘汰**：方向反转时，落在新方向矩形之外的预取瓦片**直接回收、不进濒死区**——它从未进过窗，没有可见生命周期，不需要缓冲。

队列用 `LongQueue`（环形数组、容量取 2 的幂、自动扩容）。

### 刷新操作

`update/updateRange/updateColumn/updateRow` 刷新指定范围：活跃区内的**先回收再重新 `in`**（重新绑定），濒死区内的只刷新已缓存的数据。`updateAll` 等价于原地 `seek`。

## 八、尺寸管理器（`DimenManager`）

三级优先级（`getTileWidth(列)` 按此顺序查）：

```text
1. 单独设置的尺寸（IntIntMap）
2. TileDimenProvider 提供的动态值（可选，各平台按需实现，例如按内容测量）
3. setDefault 的默认尺寸
```

修改流程 `setTileWidth(列, 宽, gravity)`：

```text
1. 宽 <= 0 → 拒绝（设置方法要求必须大于 0）
2. 边界为空 或 列越界 → 拒绝
3. 与旧值相同 → 直接返回
4. 同步濒死区内该列所有瓦片的尺寸
5. 调用引擎 updateWidth 做视窗补偿
6. 触发刷新
```

删除自定义尺寸请用 `deleteTileWidth(列, gravity)`（= `widths.remove` + 同样的同步流程），**不要用「传 0」表达删除**。`setTileSize` 把横竖两个方向合并成一次扰动。

## 九、组合调度层（`TileCoreService`）

把三个模块组合成统一入口，本身是纯逻辑，可移植。**`EventHandler`（`GestureDetector`、`Scroller`）是安卓相关的，不要移植**——各平台用自己的输入体系（触摸、鼠标、手柄）把位移转成 `sync(dx, dy)`，惯性滚动也用目标平台自己的动画机制。

调度层职责：

- 转发边界/尺寸/瓦片生命周期回调，把引擎和瓦片管理器接起来；
- 提供统一 API：`sync/seek/snap/update/setTileWidth/...`；
- 在 `onWindowCalculated` 后调用 `diffPrefetch` 规划预取，由渲染端每帧 `drainPrefetch()` 消费；
- 持有调试统计（可选）。

## 十、接入目标平台渲染层

引擎只输出「哪些瓦片可见、在哪个坐标、多大」，渲染层负责画出来：

1. 实现边界接口 / 视窗接口 / 回调（数据源与瓦片持有者）；
2. 把「视窗变化」接到目标平台的刷新机制（重绘 / 重组 / 提交渲染命令）；
3. 用目标平台的输入体系驱动 `sync`。

## 十一、测试策略

三个模块都是纯算法，非常适合单测：mock 接口，验证输出。`LayoutEngine` 验证滚动/跳转/尺寸变更下的 `LayoutModel`；`TileManager` 验证进出/回收计数与预取；`DimenManager` 验证尺寸查询与修改扰动。

**跨实现对齐（同构差分测试）**：把两份实现放进**同一份随机场景序列**（同一个伪随机数发生器、同一批列宽/行高/窗口/位移），逐场景比对 `LayoutModel` 的完整输出（锚点、`contentWidth`、`offset`）。本项目用它对齐 Java 与 H5：600 个场景（`sync`/`seek`/`updateWidth` 混合、二维数据）零差异才算移植完成。

> 伪随机数发生器的**乘数要挑小的**：乘积超过 2^53 时 JS 会丢精度，两边序列会悄悄跑偏。

边界场景清单：

- 空边界（左 > 右）
- 单列 / 单行
- 从 `Integer.MIN_VALUE` 附近起步
- 高频抖动（在同一列边界反复滚动）
- 尺寸反复修改（大到小再到大）
- 全部瓦片返回 null（稀疏）
- 内容比视窗小（填不满）
- 极端跳转（一次跨过整个 int32 空间）
- 预取首帧（无上次记录，方向未知）
- 预取方向反转（身后预取被淘汰回收）
